# Пункт плана {{name}}

Цель — пункт плана сделан так, как в нём записано, ничего лишнего не задето, и проверки это показывают.

## Порядок

### 1. Найти пункт

1. `git fetch`. Есть новое на сервере — сказать и предложить подтянуть: план мог измениться.
2. Найти пункт по номеру во всех `reviews/*/plan.md` и его находку в `review.md` того же цикла. Прочитать шапку плана «Как вести» и следовать ей. Расходится с CLAUDE.md — главнее CLAUDE.md; сказать и спросить.
3. Пункт из таблицы решений — в работу, только если заполнено «Решение». Пусто — остановиться и спросить. Решили не так, как предложено, — вписать решение в таблицу и делать по нему.
4. «Этап N» — все открытые пункты этапа по порядку, каждый как отдельный пункт.

### 2. Понять, где причина

Назвать место причины до правки:

| Пункт | Где причина | Где правка |
|---|---|---|
| REQ — требование противоречиво или неполно | действующий документ (CLAUDE.md, «Источник истины») | документ + его журнал изменений, если ведётся; затем прототип, если требование в нём отражено |
| BUG — прототип не по требованиям | прототип; или документ, если ошибка в нём | там, где причина |
| DOC | README и сопроводительные документы | документ; сгенерированные файлы — через исходник и сборку |
| DATA | демо-данные прототипа | данные |
| PROC | `tools/`, CI, договорённости | там |
| ARCH | системная причина | по пункту; частные пункты, которые на него ссылаются, — проверить после |

Поведение прототипа подтвердить до правки: открыть прототип (`python tools/kit/check_page.py`, встроенный браузер или временная страница в scratchpad) и пройти шаги из находки. Не воспроизводится — сказать, а не чинить наугад.

### 3. Исправить

- Только то, что в пункте. Нашлось другое — назвать, не чинить попутно.
- Сгенерированные файлы и архивные версии документов не править (список — CLAUDE.md).
- Требование меняется в действующем документе; прошлые версии не трогать.
- Новое поведение — с проверкой, если в проекте есть самопроверка или тесты (CLAUDE.md, «Проверки»); проверка должна падать до правки. Нет — в ответе сказать, как проверено руками.

### 4. Проверить

- Быстрые проверки и дополнительные по таблице «Что поменял → что проверить» в CLAUDE.md.
- Правка требований с идентификаторами — `python tools/kit/check_ids.py`; правка прототипа — `python tools/kit/check_page.py`.
- Проверку, которую не прогнал, назвать с причиной.

### 5. Ответ

- что сделано по пункту и где (файлы);
- итоговые строки проверок, как есть; что не прогонялось и почему;
- что нашлось попутно и не чинилось.

### 6. Коммиты — только по просьбе

Два коммита:

1. Исправление. Сообщение начинается с номера пункта: `BUG-01: Кнопка «Пропустить» — запрос причины`; несколько пунктов — через запятую.
2. Отметка в плане: `- [ ]` → `- [x]`, в пункте — `Коммит: \`<хэш>\``. Сообщение — `Хэш <хэш> в плане ревью <дата>`.

Push — только если попросили.
