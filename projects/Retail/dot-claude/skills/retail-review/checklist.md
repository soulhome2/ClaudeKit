# Чек-листы ревью Retail по ролям

Один проход, но через каждую роль по очереди. Находку можно найти глазами одной роли, а записать — с меткой всех, кого она касается. Новый тип ошибки, найденный в ревью, — пункт в раздел той роли, которая его нашла.

Разделы ТЗ v3: §3 границы, §5 компоненты и поток данных, §6 кассовые данные и универсальная модель, §7 видео и титры, §8 интерфейс «Чеки», §9 мониторинг и жизненный цикл инцидента, §10 сценарии POS / RETAIL / ANL / LOG, §11 конструктор правил, §13 API, §14 НФТ, §17 приёмка, §18 открытые вопросы, §20 журнал версии.

## Архитектор

*Вопрос: модель целостна, однозначна и переносится в продукт без переделки?*

- [ ] Граница «Интеллект X / addon» (§3, §5.1) одна во всех разделах; входной документ RS 2.0 («все функции ИХ дублируются в продукте») не противоречит ей молча — если противоречит, это вопрос в таблицу решений.
- [ ] Универсальная модель (§6.3) содержит каждое поле, которое используют сценарии §10 и конструктор §11: товар, «Честный знак», вес, тип операции, оплата, КСО-счётчики X / Y.
- [ ] Каждый сценарий §10 выражается в конструкторе правил §11 и в редакторе сценариев прототипа (модель «И из ИЛИ», `НЕ произошло`, таймеры, повторы, переменные). Невыразимые (вложенные группы) — названы явно.
- [ ] «Отсутствие POS-события» определено одинаково в §5.1 (Correlation Engine), §11 и сценариях: от какого момента отсчитывается окно, что считается «молчанием».
- [ ] Синхронизация времени (§7.4, Time Synchronization Service): допустимое смещение, что делать при рассинхроне, как это видно оператору.
- [ ] Жизненный цикл инцидента §9.2 согласован с проектом IM (`../IM`, компонент Incident Manager): статусы, переходы, классификация. Расхождение — вопрос, не находка против IM.
- [ ] Одно понятие — одно слово в ТЗ, прототипах и i18n (тревога / сработка / инцидент, сценарий / правило, КСО / касса самообслуживания).

## Тестировщик

*Вопрос: всё работает так, как написано, и заметим ли мы, если сломается?*

- [ ] `check_ids.py`: нет повторов и ссылок на несуществующие сценарии; `--unused` — сценарии без ссылок разобраны.
- [ ] Каждый сценарий §10: условие, окно времени, пороги со значением по умолчанию, приоритет, что попадает в инцидент — достаточно, чтобы написать ожидаемый результат для приёмки §17 п. 8.
- [ ] Отказы и пограничные случаи: потеря связи с кассой (буферизация и порядок, §17 п. 11), повтор события (дедупликация), постфактум-импорт без архива, рассинхрон часов, КСО с допуском X−1 / X−2.
- [ ] Критерии приёмки §17 измеримы; «согласованные показатели» (п. 14) ссылаются на числа §14.
- [ ] Прототипы открываются без ошибок (`check_page.py`) в обеих темах; изменение `scenario-editor.*` проверено в обоих.
- [ ] Редактор сценариев: неопределённые переменные не дают сохранить; шаблоны (POS-10, POS-11, RETAIL-01 и др.) собираются из тех же условий, что описаны в ТЗ.

## Продакт

*Вопрос: сделано то, что нужно, и ничего важного не потеряно?*

- [ ] Пункты входных «правок» отражены в v3 (§20) или явно отложены в §18.
- [ ] Требования документа «2026-10-25 Разработка интерфейса» (RS 2.0): какие уже в прототипе, какие нет, какие противоречат ТЗ v3 — список для решения, не ошибки.
- [ ] Сценарии в прототипе названы так же, как в ТЗ: где прототип показывает `3.2.x`, а ТЗ — `POS-NN`, связь однозначна.
- [ ] Внешние поставщики (Perfema, POS PSIM) — класс решения, не жёсткая зависимость (§18).
- [ ] Полный и упрощённый прототипы: назначение каждого понятно; функции, которых нет в одном из них, — осознанно.

## UX / оператор

*Вопрос: оператору под нагрузкой удобно и понятно?*

- [ ] Живой режим (§9.1): с плитки кассы — к чеку, видео и инциденту без смены контекста.
- [ ] Из строки чека — к моменту видео (§17 п. 4); поиск по титрам открывает полный чек (п. 6).
- [ ] Тревога → инцидент: действия и статусы §9.2 видны и доступны там, где оператор их ждёт.
- [ ] Переключение языка: все строки переведены, ничего не обрезано на английском.
- [ ] Редактор сценариев понятен без документации: пояснение (шкала, фраза, формула) совпадает с собранным условием.

## Дизайнер

*Вопрос: интерфейс собран по ONE PSIM и одинаков во всех состояниях?*

- [ ] Цвета — из `--one-*` через `bridge.css`; новые цвета вне переменных только в заглушке видео (README, решение 5).
- [ ] Новые контролы — по лестницам кита; контрол без лестницы — в «Пробелы правил», а не выдуманная лестница.
- [ ] Обе темы в обоих прототипах (полный — только Dark, пока владелец не решил иначе); снимки `check_page.py --shots` посмотреть глазами.
- [ ] Статусы и приоритеты — тройки danger / warning / info; категории источников — палитра без green / red рядом со статусами.
- [ ] Узкий экран: `check_page.py` предупреждает о горизонтальной прокрутке на 360 px — нужен ли прототипу мобильный вид, решает владелец; записать один раз.

## Разработчик

*Вопрос: можно ли взять это в работу без устных пояснений?*

- [ ] POS Gateway и Adapter Utility (§6.1, §6.2): протоколы касс, формат на выходе, ошибки разбора, дедупликация.
- [ ] Постфактум-импорт (§6.4): формат файла, привязка к архиву, отчёт об ошибках.
- [ ] API addon (§13.2): методы, права, коды ошибок; исключение платёжных реквизитов из экспорта (§17 п. 13).
- [ ] НФТ §14 — числами и с профилем нагрузки.
- [ ] Права (§4): ограничение по объектам, магазинам и функциям описано так, чтобы проверить §17 п. 10.
- [ ] Комплект поставки (§16) и установка / обновление / откат (§17 п. 15) — что именно поставляется.
