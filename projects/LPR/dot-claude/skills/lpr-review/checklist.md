# Чек-листы ревью LPR по ролям

Один проход, но через каждую роль по очереди. Находку можно найти глазами одной роли, а записать — с меткой всех, кого она касается. Новый тип ошибки, найденный в ревью, — пункт в раздел той роли, которая его нашла.

Разделы ТЗ: §5 архитектура, §6 требования M1–M13, §7 модель данных, §8 интеграции, §9 интерфейс и экраны Э1–Э10, §10 роли, §11 НФТ, §12 ИБ, §14 этапы, §15 приёмка, §17 открытые вопросы, приложение А — трассировка ФТ → ТЗ.

## Архитектор

*Вопрос: модель целостна, однозначна и переносится в продукт без переделки?*

- [ ] Граница «Интеллект X / RoadAR / Решение» (§1.1, §5.2) одна во всех разделах: функция не приписана сразу двум, ни одна не повисла без владельца.
- [ ] Конвейер события (§5.4) и модель данных (§7) согласованы: каждое поле, которое конвейер пишет или читает, есть в модели, и наоборот.
- [ ] Поля событий Webhook / MQTT (§8.2) и ответов REST (§8.1) есть в модели данных §7 с теми же именами и типами.
- [ ] Нормализация ГРЗ (кириллица / латиница, пробелы, регион) задана в одном месте; поиск, списки, сопоставление и импорт ссылаются на неё, а не описывают заново.
- [ ] Типы совпадения со списком (точное, нечёткое, по части) определены один раз и одинаково используются в M4, M5, M6.
- [ ] Конфликт правил доступа (M6) разрешается однозначно: приоритет списка, затем «отказать» сильнее «пропустить», правило по умолчанию на каждой точке.
- [ ] Автономность КПП: что работает без связи с центром, как синхронизируются проезды и списки после восстановления, без дублей.
- [ ] Одно понятие — одно слово в ТЗ и в прототипе (проезд / визит / распознавание, срабатывание / оповещение, точка / канал).

## Тестировщик

*Вопрос: всё работает так, как написано, и заметим ли мы, если сломается?*

- [ ] `check_ids.py`: нет повторов и ссылок на несуществующие требования; `--unused` — требования без ссылок разобраны.
- [ ] У каждого требования M есть проверяемый критерий: число, условие или наблюдаемый результат; у каждого `[значения]` — значение по умолчанию.
- [ ] Критерии приёмки §15.2 покрывают требования M этапа 1 (§14); требование M этапа 1 без способа проверки — находка.
- [ ] Пограничные случаи распознавания описаны: ТС без ГРЗ, двухстрочный, иностранный, частично прочитанный, грязный; ночь; повторы на одном канале (интервал объединения).
- [ ] Отказы: нет связи с центром, с RoadAR, со СКУД; шлагбаум не открылся; переполнение очереди решений.
- [ ] Прототип открывается без ошибок (`check_page.py`) в обеих темах; все экраны Э1–Э8 из §9.2 есть.

## Продакт

*Вопрос: сделано то, что нужно, и ничего важного не потеряно?*

- [ ] Приложение А покрывает каждый пункт ФТ; пункт ФТ без требования — находка или явное «не делаем» с причиной.
- [ ] Требования вне ФТ помечены «расширение» и вынесены на согласование.
- [ ] Этапы §14 согласованы с приоритетами: требование M не уехало в поздний этап без пометки, S не попало в MVP молча.
- [ ] Каждое «уточнить» в тексте есть в §17 с адресатом, и наоборот; видно, какие требования зависят от ответа.
- [ ] Прототип не показывает функции поздних этапов как готовые без пометки (как «расш.» у Нарушений).

## UX / оператор

*Вопрос: оператору КПП и СБ под нагрузкой удобно и понятно?*

- [ ] Э1: решение по проезду — один клик или одна клавиша (§9.3); горячие клавиши F2 / F4 / F6 / F8 и `Ctrl+K` одинаковы в ТЗ (UI-03, UI-04) и в прототипе.
- [ ] Очередь «ожидает решения» с таймером: что происходит по истечении — описано и видно.
- [ ] Скрытое оповещение: на КПП нет признака, у получателя — срабатывание (§15.2); прототип не выдаёт его оператору КПП.
- [ ] Ручное открытие и отказ требуют причины; причина видна в журнале.
- [ ] Каждый блок показывает состояния данные / загрузка / пусто / ошибка с «Повторить» (UI-08).
- [ ] Права из §10 отражены в прототипе: оператор КПП не видит того, что ему не положено (скрытые списки, расследования).

## Дизайнер

*Вопрос: интерфейс собран по ONE PSIM и одинаков во всех состояниях?*

- [ ] ГРЗ везде отрисован как знак (UI-01): моноширинный шрифт, отдельный регион, флаг; низкая уверенность — значок.
- [ ] Статусы списков — цвет и текст вместе (UI-02); зелёный / красный / жёлтый / серый — одни и те же везде.
- [ ] Цвета хрома — из переменных ONE PSIM, без цветов вне переменных; заглушки видео — допустимое исключение.
- [ ] Обе темы читаются; контраст текста достаточный; снимки `check_page.py --shots` посмотреть глазами.
- [ ] Минимальная ширина рабочего места КПП — 1366 px (§9.3); узкие экраны — только для просмотра, без обрезанных действий.
